# 后端设计

本文覆盖 `apps/backend` 从现有 NestJS 骨架到可用后台服务的拆分方式、认证方案、数据模型、接口契约和落地顺序。目标是把前端当前存在 `localStorage` / mock 里的活动、报名、内容推送和看板数据迁到 MySQL，同时保持现有 `{ code, msg, data }` 响应约定。

## 1. 边界与原则

- 保持模块化单体，不拆微服务，不引入 Redis / MQ；先用一个 NestJS 进程支撑运营后台。
- 成功响应继续显式 `Result.ok()`，不新增全局响应拦截器。
- 允许新增全局**异常过滤器**，只负责把 Nest 抛出的异常转换成统一失败结构，和“响应拦截器”区分开。
- 管理端接口默认全部需要登录，只有报名页和分享落地页公开。
- 富文本按 BlockNote 文档 JSON 存储，不转 HTML；摘要单独存纯文本。
- 时间统一以 UTC 入库和出参，前端按北京时间展示、筛选。
- AI 生成先保留 mock 能力，再接可配置 Provider；不让前端直接持有模型密钥。

## 2. 模块拆分

```text
apps/backend/src/
├── common/
│   ├── api-response.ts           # 已有：{ code, msg, data }
│   ├── result.ts                 # 已有：Result.ok / Result.fail
│   ├── errors/
│   │   ├── error-code.ts         # 业务错误码
│   │   └── http-exception.filter.ts
│   ├── guards/                   # 登录态、角色、请求来源和登录限流
│   └── dto/
│       ├── page-query.dto.ts
│       └── page-result.ts
├── infra/
│   └── database/                 # 连接、CLI DataSource、迁移
└── modules/
    ├── auth/                      # 会话、邀请、管理员管理
    ├── activities/
    ├── content-push/
    └── home/
```

`auth` 负责管理端登录、用户管理和邀请注册。模块实体放在 `entities/`，请求 DTO 放在 `dto/`，守卫统一放在 `common/guards/`。业务控制器通过守卫读取当前账号。

## 3. 认证与用户管理

- 管理端通过用户名和密码登录。后端签发有效期 24 小时的 JWT。浏览器保存用户资料和令牌，管理端请求使用 `Authorization: Bearer <token>`。
- 本地首次启动创建超级管理员 `admin/admin`。生产首次启动使用 `AUTH_BOOTSTRAP_PASSWORD`，长度 12–64 字符。初始化保留已有账号与密码。
- 只有超级管理员可以查看用户、生成邀请或启停普通管理员。邀请有效期 24 小时，每条邀请只能创建一个普通管理员账号。创建账号与消费邀请码使用同一事务。
- 退出时清除浏览器本地授权信息，已签发的 JWT 可用至到期。每次鉴权读取账号状态。停用期间拒绝请求，重新启用后，仍在有效期内的 JWT 恢复有效。

| 方法  | 路径                      | 说明                                  |
| ----- | ------------------------- | ------------------------------------- |
| POST  | `/auth/login`             | 返回 JWT、账号资料和会话到期时间      |
| POST  | `/auth/logout`            | 清理旧版会话 Cookie，前端丢弃本地令牌 |
| POST  | `/auth/register`          | 提交邀请码、用户名和密码              |
| GET   | `/admin/users`            | 列出管理端账号和状态                  |
| POST  | `/admin/invitations`      | 生成一次性邀请码                      |
| PATCH | `/admin/users/:id/status` | 启用或停用普通管理员                  |

## 4. 数据模型

### 4.1 管理端账号与邀请

- `admin_users` 保存 UUID、唯一用户名、scrypt 密码散列、角色、状态和创建时间。角色为 `super_admin` 或 `admin`，状态为 `active` 或 `disabled`。
- `admin_invitations` 保存令牌摘要、过期时间和消费时间。

### 4.2 `activities`

| 字段         | 类型                             | 说明                                              |
| ------------ | -------------------------------- | ------------------------------------------------- |
| `id`         | `BIGINT UNSIGNED AUTO_INCREMENT` | 自增主键，接口用十进制字符串传输                  |
| `name`       | `VARCHAR(80)`                    | 活动标题，必填，允许同名                          |
| `sharer`     | `VARCHAR(50)`                    | 分享人姓名，必填                                  |
| `event_date` | `DATE`                           | 活动日期，使用北京时间日历日，接口传 `YYYY-MM-DD` |
| `summary`    | `VARCHAR(500)`                   | 活动概要，必填，提交时为 1–100 字                 |
| `created_by` | `CHAR(36)`                       | 创建人，外键关联 `admin_users.id`                 |
| `created_at` | `DATETIME(3)`                    | 创建时间                                          |
| `updated_at` | `DATETIME(3)`                    | 最后修改时间                                      |
| `deleted_at` | `DATETIME(3) NULL`               | 软删除时间，正常活动为空                          |

- 活动列表按 `event_date DESC, id DESC` 排序，对应索引 `(deleted_at, event_date, id)`。
- 删除时填写 `deleted_at`，列表和详情排除软删除的活动，关联的报名和签到记录保留。
- 公开报名链接由后端签发，链接载荷引用活动 ID。

### 4.3 `activity_signups`

| 字段          | 类型              | 说明                                              |
| ------------- | ----------------- | ------------------------------------------------- |
| `id`          | `CHAR(36)`        | UUID 主键，由后端生成                             |
| `activity_id` | `BIGINT UNSIGNED` | 外键，关联 `activities.id`                        |
| `name`        | `VARCHAR(50)`     | 报名姓名                                          |
| `phone`       | `VARCHAR(16)`     | 中国大陆 11 位手机号，提交时去掉可选的 `+86`      |
| `inviter_id`  | `CHAR(36) NULL`   | 邀请人自己的报名 UUID，关联 `activity_signups.id` |
| `created_at`  | `DATETIME(3)`     | 报名时间                                          |

- 唯一约束为 `(activity_id, phone)`。重复报名保留首次邀请关系。
- 使用索引 `(activity_id, inviter_id)` 查询直接邀请。后端记录归因前，检查邀请人属于同一场活动。
- 从活动原始海报报名时，`inviter_id` 为空，报名页显示活动分享人信息并隐藏邀请人一栏。

### 4.4 `content_pushes`

| 字段            | 类型            | 说明                                      |
| --------------- | --------------- | ----------------------------------------- |
| `id`            | char(36)        | UUID                                      |
| `title`         | varchar(60)     | 标题                                      |
| `summary`       | varchar(200)    | 摘要                                      |
| `document`      | json            | BlockNote 文档                            |
| `tags`          | json            | AI 生成时选择的标签，可空                 |
| `prompt`        | varchar(200)    | AI 提示词，可空                           |
| `activity_id`   | BIGINT UNSIGNED | 可空，关联 `activities.id`                |
| `status`        | varchar(16)     | `draft` / `scheduled` / `sent` / `failed` |
| `scheduled_at`  | datetime(3)     | 可空；草稿为空                            |
| `sent_at`       | datetime(3)     | 可空                                      |
| `failed_reason` | varchar(200)    | 可空                                      |
| `created_by`    | char(36)        | 创建人                                    |
| `created_at`    | datetime(3)     |                                           |
| `updated_at`    | datetime(3)     |                                           |

「发送」的实际外部投递通道暂未确定，首版状态只代表站内发布记录。后续接入公众号/企微/短信时通过 `DeliveryAdapter` 扩展，不把渠道写死进表结构。

## 5. 接口契约

### 5.1 通用

```ts
interface PageResult<T> {
  items: T[]
  page: number
  pageSize: number
  total: number
}
```

- 列表默认 `page=1&pageSize=10`，`pageSize` 最大 50。
- 日期筛选使用 `startDate` / `endDate`，格式 `YYYY-MM-DD`，按北京时间解释。
- DTO 继续用 class-validator；新增字段必须写校验和中文提示。

### 5.2 活动

| 方法   | 路径              | 说明                                 |
| ------ | ----------------- | ------------------------------------ |
| GET    | `/activities`     | 分页列表，支持标题、分享人和日期筛选 |
| GET    | `/activities/:id` | 活动详情                             |
| POST   | `/activities`     | 新建活动                             |
| PATCH  | `/activities/:id` | 更新请求中提供的字段                 |
| DELETE | `/activities/:id` | 软删除，成功时返回 `data: null`      |

- 接口需要管理端登录。新建必填字段为 `name`、`sharer`、`date` 和 `summary`。手填概要为 1–100 字，AI 生成概要为 50–100 字。
- 列表可传 `keyword` 按标题搜索、`sharer` 按分享人搜索，以及 `date` 精确匹配某天（`YYYY-MM-DD`）。日期范围查询可传 `startDate` 和 `endDate`，两端都包含。
- 活动 ID 在路径和 JSON 响应中使用十进制字符串。不存在或已软删除的活动返回 HTTP 404。

| 方法 | 路径                                  | 说明                                           |
| ---- | ------------------------------------- | ---------------------------------------------- |
| POST | `/activities/:id/poster-qr`           | 管理端签发原始报名链接，并返回二维码点阵。     |
| GET  | `/public/activities/invite?token=...` | 验签后读取活动和邀请人信息，兼容旧链接的展示。 |
| POST | `/public/activities/:token/signups`   | 提交姓名和手机号，成功后返回报名凭证。         |
| POST | `/public/activities/poster-qr`        | 报名者凭报名凭证生成专属报名链接和二维码。     |

报名在同一事务内校验活动、校验邀请人属于同一活动并写入报名记录。数据库唯一约束拒绝同场活动的重复手机号，接口返回 HTTP 409 并保留首次邀请关系。

活动原始链接包含活动 ID，专属链接同时包含邀请人报名 UUID `inviterId`。旧 Base64 活动链接可展示原有活动信息，正式报名需使用新签发的链接。测试功能里的报名演示继续使用浏览器记录。

### 5.3 内容推送

| 方法   | 路径                | 说明                             |
| ------ | ------------------- | -------------------------------- |
| GET    | `/pushes`           | 分页列表，支持关键词、状态、活动 |
| GET    | `/pushes/:id`       | 详情                             |
| POST   | `/pushes`           | 新建草稿/定时/已发送记录         |
| PATCH  | `/pushes/:id`       | 编辑                             |
| DELETE | `/pushes/:id`       | 删除                             |
| POST   | `/pushes/:id/retry` | 失败重试                         |
| POST   | `/pushes/generate`  | AI 初稿；结合标题、标签、提示词  |

创建/编辑时由服务端根据 `scheduledAt` 计算状态：

- 显式保存草稿 → `draft`。
- 无发送时间且非草稿 → `sent`，写入 `sent_at`。
- 发送时间在未来 → `scheduled`。
- 定时任务到点执行 → `sent` / `failed`。

首版不做多实例调度锁；单实例用 `@nestjs/schedule` 每分钟扫描一次到期的 `scheduled` 记录。后续多实例时增加 `locked_at` 或独立任务队列。

### 5.4 首页

`GET /home/overview?startDate&endDate&activityId` 保持现有路径，替换 Mock 实现：

- 活动次数：活动日期落在区间内的活动数。
- 报名人数：区间内 `activity_signups.created_at` 的有效报名人次；同一活动同一手机号只算一次。
- 内容推送次数：发送时间落在区间内且 `status !== 'draft'` 的记录数，可选按活动过滤。
- 趋势图：按报名日期聚合每日报名人数。

## 6. 前端接入顺序

1. 新增 `apps/web/src/lib/api-client.ts`，统一 `baseURL = VITE_API_BASE_URL`、`credentials: 'include'`、`{ code, msg, data }` 解析和 401 跳转。
2. 登录页改为调用 `POST /auth/login`；浏览器保存返回的账号资料和会话到期时间供刷新后恢复；退出调用 `POST /auth/logout` 后清理本地资料。
3. 活动页通过 `/activities` 获取和保存活动，保留表单校验与海报绘制。
4. 报名页通过后端提交报名，浏览器保存报名凭证供刷新后继续使用专属海报。
5. 内容推送页把 `push-storage` 替换为 `/pushes`；编辑器文档继续提交 BlockNote JSON。
6. 看板从 `demoReport` 切到 `/home/overview`。
7. 所有列表接口统一走 React Query，分页参数和前端 shadcn 分页组件对齐。

## 7. 环境变量与迁移

新增：

```bash
AUTH_JWT_SECRET=生产必填，至少 32 字符的随机密钥
AUTH_BOOTSTRAP_PASSWORD=生产空库首次启动使用，12–64 字符
ACTIVITY_LINK_SECRET=活动链接及报名凭证的稳定签名密钥
```

- 密码只在初始化时使用，seed 成功后不覆盖已有账号。本地留空 JWT 密钥时，每次启动会生成新密钥。活动链接优先使用 `ACTIVITY_LINK_SECRET`，其次使用 `AUTH_JWT_SECRET`。开发环境两者都留空时，重启会使已有签名链接和报名凭证失效。
- 新实体必须同时加入模块 `TypeOrmModule.forFeature()` 和 `src/infra/database/data-source.ts` 的 `entities`。
- 生产必须 `DATABASE_SYNCHRONIZE=false`，本地可开自动同步；已有 `AdminAuth` 迁移，业务表随模块交付迁移。

## 8. 安全与稳定性

- 登录失败统一提示“用户名或密码错误”，不区分账号是否存在。
- 登录限流：同 IP + 用户名 5 次/分钟；单 IP 20 次/分钟；首版用进程内计数，后续换 Redis。
- 公开报名限流：单 IP 10 次/分钟，并对手机号做基本格式校验。
- 密码和 JWT 不写日志。公开报名接口不发送管理端令牌。
- CORS 只放行配置来源，保持 `credentials: true`。
- 统一异常过滤器隐藏 SQL、堆栈等内部细节，500 只返回“系统错误，请稍后重试”。

## 9. 实施阶段

### Phase 1：认证闭环

- `admin_users` 实体与初始化管理员。
- `POST /auth/login`、`POST /auth/logout`、JWT 守卫。
- 登录页、用户 popover 退出、应用启动恢复登录态接真实接口。
- 验收：错误密码失败、正确登录进入后台、刷新仍保持登录、退出后受保护接口返回 401。

### Phase 2：活动与报名

- `activities`、`activity_signups` 表与 CRUD。
- 公开报名接口与重复手机号处理。
- 活动页、报名页替换 localStorage。
- 验收：新建/编辑/删除活动，公开链接报名，后台列表与报名人数实时更新。

### Phase 3：内容推送

- `content_pushes` 表、分页、定时状态、失败重试。
- AI 初稿生成服务。
- 定时扫描器与投递适配器接口。
- 验收：草稿、定时、发送、失败重试状态流转正确；AI 结合标题生成。

### Phase 4：看板与加固

- `/home/overview` 真实聚合。
- 异常过滤器、错误码、登录限流、基础审计日志。
- 验收：看板与业务表数据一致，刷新、分页、异常场景稳定。
